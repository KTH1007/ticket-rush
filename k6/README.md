# k6 부하 측정

## 좌석 지도 (`seat-map.js`)

`GET /api/events/{id}/seats/layout`과 `seats/status`를 반복 호출한다. 이슈 #127의 측정에 쓴 스크립트다.

```bash
k6 run --summary-export=result.json \
  -e BASE=http://127.0.0.1:18082 -e EVENT_ID=1 \
  -e PATHNAME=seats/status -e VUS=50 -e DURATION=20s \
  k6/seat-map.js

# 배치는 gzip을 명시해야 서버의 gzip 응답 경로를 잰다. ENCODING=identity면 서버가 풀어서 주는 예외 경로를 잰다
k6 run -e BASE=... -e EVENT_ID=1 -e PATHNAME=seats/layout -e ENCODING=gzip -e VUS=10 k6/seat-map.js
```

| 환경변수 | 설명 | 기본값 |
|---|---|---|
| `BASE` | 대상 서버 주소. 필수 | |
| `EVENT_ID` | 공연 id. 필수 | |
| `PATHNAME` | `seats/layout` 또는 `seats/status`. 필수 | |
| `VUS` | 동시에 요청을 반복하는 가상 사용자 수 | 10 |
| `DURATION` | 실행 시간 | 20s |
| `ENCODING` | `Accept-Encoding` 값. 비우면 보내지 않는다 | |

200이 아닌 응답이 하나라도 있으면 요약과 `--summary-export` 파일은 그대로 나오지만 종료 코드는 0이 아니다(과부하로 일부가 실패한 측정도 실패로 끝난다).

## 대기열 (`measure-queue.sh`)

`k6/measure-queue.sh`가 일회용 환경(`k6/docker-compose.measure.yml`, 프로젝트명 `tr-measure`)을 올리고, 단계를 순서대로 돌리고, 결과를 `k6/results/<시각>/results.md`(git 무시)에 남기고, 환경을 지운다. 개발용 스택(`tr-redis`, `tr-postgres`)과 이름과 포트가 겹치지 않는다. docker, k6, python3가 필요하고 전화번호 암호화 키는 러너가 만든다.

```bash
STAGES="N3R N6A" ./k6/measure-queue.sh        # 고른 단계만 돌린다
QUICK=1 STAGES="Q1 M4" ./k6/measure-queue.sh  # 규모를 줄여 스크립트만 검증한다
KEEP=1 STAGES="..." ./k6/measure-queue.sh     # 끝나도 환경을 지우지 않는다
```

앱은 2코어와 힙 512MiB(컨테이너 1GiB)로 묶고, 부하는 nginx(18080)로 보내고 앱 지표는 직접 포트(18081)로 읽는다. 부하기가 서버와 같은 머신이라 서버가 먼저 한계에 닿게 작게 묶은 것이고, 결과는 "2코어 앱 1대의 상대 비교"로 읽는다.

| 묶음 | 단계 | 재는 것 |
|---|---|---|
| 앱 직접(nginx 없이) | S1, S2, S3, S4, S6 | 줄서기 한계 곡선, 오픈 순간, 대기자 수별 메모리와 순번 조회 용량, 승격 중 조회, 조회 폭주 |
| nginx 입구 | N0, N2, N3, N4, N5, N6 | nginx 경유 기준선, 상한 후보 비교(줄서기와 순번 조회), nginx 자체 한계 |
| 과부하와 규모 | C2, P1, A2, A3 | 재시작 직후의 차가운 앱, 50만 명 20초 피크 모델, 앱 2대 |
| 홀드와 결제 | D1, D2, D3, PG | 승격 속도별, 홀드 도착 속도별과 대기열 없는 대조군, 충돌 폭주의 DB 연결 사용, PG 지연 |
| 혼합과 전체 흐름 | M1, M2, M3, M4, F1, F2 | 순번 조회와 홀드 동시 부하, 속도 제한 효과, 지연 원인 가르기, 조회 간격 정책 효과, 상한을 건 전체 흐름 |
| 토큰과 조회 정책 | E1, Q1, N3R, N3A, N6A | 토큰 갱신 동작, 대기자 N명의 초당 조회 요청 계산, 변경 뒤 조회와 줄서기 처리량 |

| 스크립트 | 용도 |
|---|---|
| `queue.js` | `SCENARIO`로 줄서기(`register`), 토큰 채우기(`fill`), 오픈 전 등록(`preopen`), 순번 조회(`poll`), 조회 폭주(`burst`), 50만 명 20초 피크(`peak`)를 도착률로 고정해 보낸다 |
| `journey.js` | 사용자 한 명의 전체 흐름(줄서기, 503 재시도, 순번 조회, 홀드, 결제) |
| `hold.js` | 활성 토큰으로 홀드와 결제를 정해진 속도(`MODE=rate`) 또는 한꺼번에(`MODE=burst`) 보낸다 |
| `nginx-raw.js` | 앱을 거치지 않는 응답으로 nginx 자체의 처리 한계를 잰다 |
| `summarize-queue.py`, `summarize-db.py` | k6 요약과 docker stats 표본, 전후 스냅샷을 마크다운 표로 바꾼다 |

### 503 재시도 규칙

nginx가 동시 처리 상한을 넘긴 요청에 503(`SERVER_BUSY`)과 `Retry-After`(3, 5, 7, 10초 중 하나)를 준다. 클라이언트는 `Retry-After`와 순번 조회 응답의 `nextPollIntervalMs` 중 큰 값만큼 기다린 뒤 다시 보낸다. 순번 조회가 거절돼도 순번은 유지된다. 줄서기가 거절되면 순번이 아직 없고, 재시도가 성공한 시점이 순번이라 먼저 누른 순서는 보장되지 않는다.

### 재현할 때 더 지킬 것

- 거절당하는 요청도 nginx와 호스트의 CPU를 쓴다. 거의 다 거절되는 부하에서도 같은 머신의 홀드가 느려졌으므로, 순번 조회나 줄서기 부하를 홀드와 같이 잴 때는 받아주는 요청과 거절당하는 요청을 나눠서 해석한다.
- 단계 사이에 TIME_WAIT가 빠지기 전에 다음 단계를 시작하면 서버와 무관하게 모든 요청이 실패한다. 러너의 `settle`이 기다린다.
- nginx를 막 다시 띄운 직후 수천 명이 한꺼번에 접속하면 연결이 끊겨 등록이 모자란다. 토큰 채우기는 모자라면 다시 채우고, 속도 제한을 건 상태에서는 채우지 않는다(제한 전에 채운다).
- 앱을 다시 띄운 직후의 첫 단계는 JIT가 식은 상태라 낮게 나온다. 후보를 비교할 때는 단계마다 예열한다.
- 단계가 앱 이미지를 다시 빌드하므로 측정 중에는 `src`를 고치지 않는다. 러너를 고칠 때도 복사본으로 돌린다(bash는 스크립트를 읽으면서 실행한다).

## 재현할 때 지킬 것

- **공유 환경이 아니라 일회용 환경에서 돌린다.** 개발용 DB와 Redis, 이미 떠 있는 앱을 대상으로 삼지 않는다. 예: 앱 이미지를 빌드해 임시 Postgres, Redis와 같은 네트워크에 띄우고 `scripts/seed-event.sql`로 좌석 30,000석을 넣은 뒤 다른 포트(예: 18082)로 연다.
- 앱은 `docker-compose.app.yml`과 같은 메모리 제한(`mem_limit: 1g`)으로 띄운다. 제한이 없으면 Docker VM 전체 메모리를 기준으로 힙이 정해져 결과가 달라진다.
- VU는 응답을 받으면 쉬지 않고 다음 요청을 보내는 가상 사용자라서 "VU 50 = 사용자 50명"이 아니다. 믿을 만한 수치는 초당 처리량이다. 초당 도착 수를 고정하려면 `constant-arrival-rate` 시나리오가 필요하다.
- 부하기가 같은 머신에서 CPU를 나눠 쓰면 서버의 최대치가 아니라 그 조건에서의 값이 나온다.
