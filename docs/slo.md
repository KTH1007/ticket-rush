# SLI와 SLO

서비스가 "잘 동작한다"를 숫자로 정의하고, 부하 테스트와 운영 지표가 같은 기준을 쓰게 하는 문서다. 아래 값은 초안이고, 처음 4주의 실측으로 조정한다.

## 용어

| 용어 | 뜻 | 이 프로젝트의 예 |
|---|---|---|
| SLI | 서비스 수준을 재는 숫자. 보통 "좋은 요청 수 / 전체 유효 요청 수" | 순번 조회 중 5xx 없이 끝난 비율, 100ms 안에 끝난 비율 |
| SLO | SLI가 이 정도는 돼야 한다는 목표와 기간 | 28일 동안 순번 조회의 99.9%가 성공하고 99%가 300ms 안에 끝남 |
| SLA | 고객과 맺는 계약(어기면 보상). SLO보다 느슨하게 잡음 | 없음 |
| 에러 버짓 | `100% - SLO`, 허용되는 실패량 | 99.9%면 1,000건 중 1건까지 실패해도 목표 안 |

- 지연은 평균이 아니라 "임계 안에 끝난 비율"로 정한다. 평균은 느린 소수를 가린다. 아래 표의 p95, p99는 그 비율의 임계값이다.
- 100%를 목표로 잡지 않는다. 올릴수록 비용과 속도를 희생하고, 사용자는 99.9%와 99.99%의 차이를 거의 못 느낀다.

## 대상과 목표

기준은 README의 목표 규모(좌석 30,000석, 대기열 최대 500,000명, 줄서기 2,000 TPS, 승격 100 TPS) 안에서 사용자가 겪는 것이다. 측정 기간은 운영 가정으로 28일 롤링이고, 부하 시험에서는 단계별로 본다.

| 요청 | 좋은 응답 | 의도된 거절(실패로 세지 않음) | p95 | p99 | 가용성 |
|---|---|---|---|---|---|
| 줄서기 `POST /api/events/{id}/queues` | 201 | 409(오픈 전, 시작 뒤), 429(IP 한도), 503 `QUEUE_FULL` | 200ms | 500ms | 99.9% |
| 순번 조회 `GET /api/events/{id}/queues/me` | 200 | 401(없거나 만료된 토큰) | 100ms | 300ms | 99.9% |
| 공연 목록 `GET /api/events` | 200 | 없음 | 200ms | 500ms | 99.9% |
| 공연 상세 `GET /api/events/{id}` | 200 | 없음 | 200ms | 500ms | 99.9% |
| 좌석 상태 `GET /api/events/{id}/seats/status` | 200 | 없음 | 100ms | 200ms | 99.9% |
| 좌석 배치 `GET /api/events/{id}/seats/layout` | 200 | 없음 | 150ms | 300ms | 99.9% |
| 좌석 홀드 `POST /api/events/{id}/seats/hold` | 201 | 403(승격 전, 활성 만료), 409(좌석 충돌, 1인 2매 초과) | 300ms | 1s | 99.9% |
| 결제 승인 `POST /api/reservations/{id}/payments` | 201 | 409(PG 거절 등) | 1s | 3s | 99.5% |
| 예약 조회 `POST /api/reservations/lookup` | 200 | 404(틀린 번호), 429(시도 한도) | 200ms | 500ms | 99.9% |
| 예약 취소 `POST /api/reservations/cancel` | 200 | 409(이미 취소 등) | 1s | 3s | 99.5% |

- 결제와 취소는 Toss 호출을 포함해서 가용성을 낮게 잡았다. PG 장애로 인한 503은 실패로 세되, 원인을 따로 보려고 `PAYMENT_GATEWAY_UNAVAILABLE`을 구분해 본다.
- 좌석 배치는 응답이 크다(gzip 250KB, 풀면 2.5MB). 부하 시험에서는 본문을 풀지 않고 버려서 서버 응답과 전송 시간만 잰다. 본문을 풀면 부하기가 병목이 되어 같은 서버가 TTFB 65ms인데 총 1.5초로 나온다. 사용자 쪽 다운로드 시간은 회선에 달려 SLO에 넣지 않는다.
- 좌석 배치는 사용자가 들어올 때 **한 번** 내려받고 이후에는 `ETag`와 `Cache-Control`로 클라이언트가 캐시하는 것을 전제로 한다. 그래도 새 사용자는 한 번씩 내려받고, 앱은 이 응답을 내는 데 요청당 CPU 약 20ms를 쓴다(좌석 상태의 약 17배). 그래서 nginx가 앞단 캐시(`proxy_cache`)로 앱의 `Cache-Control`(60초)을 따라 응답을 들고 있다. 캐시가 빈 순간의 동시 요청은 앱에 한 번만 보내고(`proxy_cache_lock`), 만료되면 낡은 응답을 내주면서 뒤에서 한 번만 갱신하며, 앱이 죽어도 만료된 응답을 계속 내준다. 이 동작은 `k6/check-layout-cache.sh`가 확인한다. ALB만 앞에 두는 환경에는 이 캐시가 없으므로 CDN이 필요하다.
- 측정 기준: 부하 시험에서는 k6가 잰 요청 시간이다. nginx `$request_time`은 요청의 첫 바이트를 받은 뒤 응답의 마지막 바이트를 보낼 때까지라 클라이언트와 네트워크 구간을 포함한다. 서버 처리 시간만 보려면 `$upstream_*`와 앱의 느린 요청 로그(elapsedMs)를 쓴다.
- 값의 출처: 줄서기 p95 약 90ms(과부하 12,000/s 도착), 순번 조회 p95 약 50ms(과부하 10,000/s 도착), 홀드 p95 177ms(승격 100/s)처럼 이미 잰 값에 여유를 둔 출발점이다. 한 대의 Mac에서 부하기와 서버가 함께 돈 측정이라 확정값이 아니다.

## 의도된 거절을 실패로 세지 않는 이유

`QUEUE_FULL`은 서비스가 과부하를 막으려고 일부러 하는 정상 동작이다. 실패로 세면 대기열이 가득 찰 때마다 SLO가 깨져서, 정말 장애일 때와 구분되지 않는다. 대신 거절은 따로 센다.

| 가드 지표 | 보는 것 |
|---|---|
| 의도된 거절률(`queue.register.rejected`, 응답 코드별 건수) | 평소보다 높으면 용량 부족이나 공격의 신호. SLO가 아니라 용량 계획용. **앱에 닿은 거절만 센다.** `QUEUE_FULL`은 nginx가 1~2초 재사용하므로 폭주 때 실제 거절 수보다 훨씬 적게 나온다(R1: 209,954건 중 810건). nginx 접근 로그는 느린 요청만 남겨 HIT 거절 수도 없다. 실제 거절 수가 필요하면 nginx에서 따로 집계해야 하고 아직 하지 않았다 |
| 홀드 409 비율 | 좌석 경쟁이 심한 정도 |

## 정합성 SLO

숫자 비율로 못 세는 약속이다. 어기면 건수와 상관없이 장애로 본다.

| 약속 | 확인 방법 |
|---|---|
| 같은 좌석을 두 명에게 팔지 않는다 | e2e 시나리오 E13, DB 점검: `PAID` 예약의 `quantity`와 그 예약을 가리키는 `SOLD` 좌석 수가 다른 행이 없어야 함 |
| 결제가 승인됐는데 예약이 확정되지 않은 채로 남지 않는다 | e2e 시나리오 E22(회수 스케줄러), `PENDING` 결제의 체류 시간 |
| 환불이 필요한 건은 24시간 안에 사람이 처리한다 | 기존 알림 `PaymentRefundBacklogStale` |

## 측정 방법

- **부하 시험**: `k6/slo-flow.js`가 흐름과 읽기 API를, `k6/queue.js`가 줄서기와 순번 조회의 높은 도착률을 맡는다. `slo-flow.js`의 임계값은 위 표를 그대로 쓰지만 `queue.js`의 임계값은 지표 수집용(`max>=0`, `rate>=0`)이라 SLO를 판정하지 않는다. 두 스크립트 모두 `k6/slo-check.py`가 실행 뒤에 한 표로 판정한다.
- **운영(Prometheus)**: p95, p99를 계산하려면 `http_server_requests_seconds` 히스토그램이 필요하다. 설정에 없어서 기본값(건수, 합, 최대만 나옴)이었기 때문에 `management.metrics.distribution`에 히스토그램과 위 임계값의 버킷을 켠다.
- **느린 요청 추적**: nginx 접근 로그(느린 요청과 서버 오류만, `$request_time`과 `$upstream_*`)와 앱의 느린 요청 로그를 요청 id로 잇고 `k6/slow-requests.py`가 표로 낸다. 읽는 법과 ALB 필드 대응은 `docs/slow-requests.md`에 있다.

## 에러 버짓 사용 방침

- 28일 동안 버짓의 절반 이상을 썼으면 위험 있는 변경(설정 변경, 큰 리팩터링)을 미루고 원인부터 본다.
- 버짓을 다 썼으면 새 기능 배포를 멈추고 안정화만 한다.
- 버짓이 많이 남으면 실험(부하 시험, 설정 조정)을 적극적으로 한다.

| 부하 | 결과 | 앱 CPU 평균/최대 | Postgres CPU 평균/최대 |
|---|---|---|---|
| 줄서기 2,000/s, 59,997건 | p95 1ms, p99 3ms, 실패 0. **충족** | | |
| 순번 조회 3,000/s, 89,967건 | p95 1ms, p99 2ms, 실패 0. **충족** | | |
| 흐름 40명/s + 읽기 300/s | 10개 API 모두 **충족**. 줄서기 p95 1ms, 홀드 6ms, 결제 7ms, 좌석 배치 1ms | 50% / 102% | 14% / 24% |

| 흐름 120명/s + 읽기 300/s | 모두 **충족**. 홀드 3ms, 결제 p95 8ms, p99 23ms | 53% / 79% | 24% / 41% |

- 줄서기와 순번 조회 행은 직전 전체 실행(같은 하네스)의 값이고, 흐름 행은 마지막 실행의 값이다. 모든 흐름 단계에서 k6가 놓친 반복은 0건이라 목표 도착률을 그대로 걸었다.
- 정합성 점검은 모든 실행에서 이상이 없었다(좌석 수가 어긋난 확정 예약 0건, 1분 넘게 남은 `PENDING` 결제 0건).
- 120명/s는 승격 상한(초당 100)을 넘는다. 그래서 대기자가 쌓이고 7,200명 중 131명은 60초 안에 승격되지 못해 포기했다. 이는 설계대로의 대기 동작이고 SLO 위반이 아니다. 홀드 거절(좌석 충돌, 승격 전)은 2,113건으로 "제외" 열에 센다.
- 같은 구성을 앞서 한 번 더 걸었을 때(40, 80명/s)도 모두 충족이었고 앱 CPU 평균은 58%, 60%로 비슷했다.

| 120명/s | 있음 | 53% / 79% | 1ms / 2ms | 1ms | 8ms | 충족 |

- **이 환경에서 캐시는 SLO를 지키느냐 못 지키느냐를 가르지 않았다.** 없어도 모두 충족이다. 달라진 것은 앱 CPU 여유다. 캐시가 없으면 80~120명/s에서 앱 CPU 평균이 131~147%이고 최대가 컨테이너 한도(200%)에 닿는다. 있으면 40~120명/s 전 구간에서 평균 49~53%로 거의 일정하다. 좌석 배치 응답이 앱 CPU를 먹는 몫이 사라졌기 때문이다.
- 캐시는 앱의 CPU 여유를 사는 장치다. 오픈 순간처럼 새 사용자가 몰릴 때 줄서기, 홀드, 결제가 배치 응답에 CPU를 빼앗기지 않게 한다. 한계가 어디인지는 이 비교로 알 수 없다(캐시 없는 구성도 120명/s에서 통과했다).
- 지연 차이는 SLO 기준(결제 1초)에 비하면 작다. 같은 조건의 실행도 흔들린다. 캐시가 없는 80명/s의 결제 p95는 앞선 실행에서 154ms, 이번에 15ms였다(앞선 실행은 k6가 반복 67건을 놓쳤다). 조건당 1회 측정의 한계다.

### 앱 2대 (흐름 120명/s, 캐시 있음): 왜 더 느린가

SLO는 모든 실행에서 충족했지만 앱 2대가 1대보다 느렸다. 같은 조건(둘 다 새로 띄워 같은 예열 뒤 120명/s)으로 11번 짝지어 쟀고 10번은 2대가 느렸다(결제 p95 13~41ms 대 7~14ms, 차이는 1.0배에서 4.5배로 실행마다 흔들림). 한 번은 같았다.

#### 가려낸 것

| 가설 | 시험 | 결과 |
|---|---|---|
| 예열이 달랐다 | 2대 구간의 예열이 다른 공연의 좌석으로 돌던 하네스 버그를 고쳐 다시 측정 | 아님. 고친 뒤에도 2대가 느림(결제 p95 41ms 대 9ms) |
| DB 연결 풀 | 2대의 풀을 10으로 줄여 연결 총수를 1대와 같게 | 아님. 같은 차이(결제 p95 21ms). 연결 대기 시간도 0.01~0.07ms |
| Postgres CPU 한도(스로틀링) | `cpu.stat`의 멈춘 구간을 재고, Postgres 코어를 2개에서 4개로 번갈아 3쌍 | 아님. 멈춘 구간 0~2개(809구간 중), 코어를 늘려도 총 실행 시간이 같음(9.0~16.6초 대 9.1~19.6초) |
| 두 앱의 스케줄러와 스냅샷 갱신이 쿼리를 늘림 | `pg_stat_statements`로 쿼리별 호출 수와 시간 | 아님. 호출 수는 +2~3%(290,606 대 299,205), 늘어난 좌석 스냅샷 읽기는 총 0.4초 |
| VM의 CPU 경합 | PSI(커널의 CPU 대기 시간) | 거의 아님. 80초 중 1.0초(1대)와 1.7~2.1초(2대) |

#### 관측된 것

- 일의 양(쿼리 호출 수)은 같은데 모든 쿼리가 고르게 느려졌다. Postgres 총 실행 시간이 7.0~7.8초(1대)에서 9.0~19.6초(2대)로 늘었고, 특정 쿼리가 아니라 하찮은 `select`까지 두 배 가까이 느렸다. 앱도 같은 일에 CPU를 두 배 가까이 썼다(앱 CPU 합계 61~67% 대 120~148%). DB 연결을 쥐는 시간은 체크아웃당 0.59ms에서 1.0~1.16ms가 되었다.
- **앱을 늘리지 않고 앱이 아닌 CPU 부하(바쁜 루프)만 앱 1대 옆에 얹어도 같은 느려짐이 생겼다.** 두 라운드 모두 바쁜 루프가 0, 2, 4개로 늘수록 단조롭게 커졌다.

| 바쁜 루프 | 결제 p95 (1회차 / 2회차) | 앱 CPU 평균 | Postgres 총 실행 | DB 연결 쥔 시간 평균 |
|---|---|---|---|---|
| 0개 | 7 / 7ms | 61% / 65% | 6.3 / 6.9초 | 0.40 / 0.42ms |
| 2개 | 14 / 30ms | 77% / 91% | 9.0 / 10.2초 | 0.84 / 1.32ms |
| 4개 | 42 / 68ms | 122% / 131% | 16.1 / 20.7초 | 2.39 / 3.96ms |

#### 결론

- **가장 유력한 이유는 시험 환경이다.** 이 측정은 한 대의 Mac(M4, 성능 코어 4개와 효율 코어 6개)의 Docker VM(vCPU 10개) 안에서 부하기, nginx, 앱, Postgres, Redis를 모두 돌린다. 이 안에서 CPU를 쓰는 일이 늘면 앱과 Postgres가 같이 느려지고, 앱 2대는 그 CPU 사용을 늘린 한 가지 방법일 뿐이었다. 앱 대수 자체가 원인이라는 증거는 없다.
- **확정하지 못한 것**: 느려지는 메커니즘(느린 코어로의 배치, 클럭, 열)은 직접 보지 않았다. CPU 대기(PSI)와 스로틀링으로는 설명되지 않아 코어 종류나 클럭 차이로 추정할 뿐이다. 앱이 별도 호스트에서 도는 실제 구성에서는 이 느려짐이 같은 크기로 나타난다고 볼 근거가 없고, 반대로 "앱을 늘리면 용량이 는다"는 결론도 이 환경에서는 낼 수 없다.
- 하네스 버그를 하나 찾아 고쳤다. 앱 2대 구간의 예열이 다른 공연의 좌석 번호로 돌아 홀드가 성공하지 못했다. 결론을 바꾸지는 않았지만(고친 뒤에도 2대가 느림), 앞서 "예열이 달라서일 수 있다"고 쓴 가설을 검증하다 발견했다.

#### 무엇이 느렸나

기본 실행의 홀드, 결제, 예약 조회, 공연 목록과 상세, 순번 조회가 목표를 넘었고, 홀드와 결제 일부는 500으로 끝났다. 줄서기 폭주 요청의 1.99%와 순번 조회의 9.75%는 의도된 거절이 아닌 실패였다(nginx 동시 연결 상한 503, 504, 취소된 연결).

#### 어떻게 관측했나 (위에서 아래로 좁혀 감)

1. **k6 요약(`slo-check.py`)**: 어느 API가 어떤 SLO(p95, p99, 가용성)를 어겼는지.
2. **nginx 느린 요청 로그(`slow-requests.py`)**: 100ms 이상 49,714건 중 앱 밖 구간(nginx 대기, 클라이언트)이 절반 이상인 요청은 0건이었다. 느린 시간은 nginx나 클라이언트가 아니라 앱 구간(`upstream_time`)에서 쓰였다.
3. **시간대 분포**: 느린 요청의 62%(31,095건)와 500 응답 대부분(723건)이 부하 시작 후 40초에 몰렸다. 60초 뒤에는 느린 요청이 20초당 1,000건 안팎으로 줄었다.
4. **자원 시계열**: 같은 40초 동안 앱 CPU가 210%(컨테이너 한도 200%)였고 Hikari 연결 20개가 전부 사용 중, 연결을 기다린 스레드가 최대 774였다. Postgres CPU는 평균 31%, Redis 18%였다.
5. **앱 로그**: `Connection is not available, request timed out (total=20, active=20)` 441건, `CannotCreateTransactionException`으로 인한 `처리되지 않은 예외` 437건이 500 응답이 되었다(결제 230, 홀드 95, 그 밖 111). Postgres의 100ms 이상 쿼리는 1건이었다.
6. **변형 실행으로 가르기**: 같은 부하에서 예열을 늘리거나 한 부하를 끄고 다시 쟀다.

#### 원인

- **확인한 것**
  - 가벼운 예열로 시작한 실행은 5번 모두(기본 1번과 예열 켬/끔 비교 4번) 위반이 있었다. 반면 같은 부하를 60초 먼저 걸어 데운 실행은 1번 모두 충족했다(앱 CPU 평균 152%, Hikari 대기 0). 이쪽은 반복하지 않아 정상 상태 용량이 충분하다고는 단정하지 못한다.
  - 실패는 부하 시작 직후 40초에 집중됐다. 그 구간에서 앱 CPU가 한도에 닿았고 DB 연결 풀(20)이 고갈됐다.
  - 가벼운 예열에서 순번 조회와 줄서기 폭주 중 하나만 꺼도 흐름 API는 통과했다(각 1회). 둘이 겹쳐 시작할 때 깨졌다.
  - 줄서기 폭주 2,000/s의 거절 처리가 앱 CPU를 많이 쓴다. 폭주를 끈 실행(앱 CPU 평균 109%)이 켠 실행(152%)보다 약 43%p 낮았다. 두 실행의 예열이 달라 정확한 몫은 아니다.
  - DB는 병목이 아니었다. Postgres CPU 평균 31%, 느린 쿼리 1건.
- **추정(직접 증명하지 않음)**: 덜 데워진 JVM은 요청당 CPU가 커서 총 수요가 2코어를 넘고, 그러면 DB 연결을 쥔 시간이 길어져 풀(20)이 고갈되고, 연결을 못 얻은 요청이 500이 된다. 시간 순서(CPU 210% -> 풀 20/20 -> 대기 774 -> 타임아웃 441)는 이와 맞지만 연결 점유 시간을 직접 재지는 않았다.
- **확인하지 못한 것**
  - 같은 부하 60초 예열이 통과한 이유(JIT, 연결 풀 확장, 캐시, 쓰기 경로). 안전한 읽기 경로만 부르는 예열은 아래와 같이 재현되는 효과가 없었다.
  - 정상 상태에서도 120~200초에 Hikari 20개가 가득 차는 순간이 40초 간격으로 세 번 있었다(순번 조회를 끈 실행에서 대기 스레드 12, 45, 25). 좌석이 차면서 홀드 충돌 재시도가 늘어나는 시기와 겹치지만 원인은 확인하지 못했다.
  - 순번 조회를 끈 실행의 줄서기 폭주 중 의도하지 않은 실패 1,375건이 정확히 어떤 응답인지(nginx 동시 연결 상한의 503으로 추정, 응답 본문 코드는 로그에 없다).

#### readiness 예열 시도: 효과를 가리지 못함

기동 직후 읽기 경로를 자기 자신에게 20초 호출한 뒤에야 readiness가 UP이 되게 하는 예열(`StartupWarmup`)을 구현해 같은 부하에 번갈아 두 쌍을 걸었다. 줄서기, 홀드, 결제는 운영 데이터와 알림에 부작용이 생겨 부르지 않았고, 공연 목록, 상세, 좌석 상태와 배치, 가짜 토큰의 순번 조회만 부른다.

| 쌍 | 예열 | readiness UP까지 | 순번 조회 가용성 | Hikari 대기 스레드 최대 | 500, 502, 504 응답 |
|---|---|---|---|---|---|
| 1 | 켬 | 28초 | 98.04% | 49 | 292 |
| 1 | 끔 | 7초 | 93.72% | 171 | 206 |
| 2 | 켬 | 28초 | 88.36% | 569 | 413 |
| 2 | 끔 | 8초 | 98.45% | 124 | 129 |

- 한 쌍에서는 켠 쪽이, 다른 쌍에서는 끈 쪽이 좋았다. 예열의 차이가 실행마다 흔들리는 값보다 작아서 효과를 확인하지 못했다. 네 실행 모두 위반이 있었다.
- readiness가 예열 동안 막혀 있는 것(UP까지 7초 대 28초)은 확인했다. 효과가 입증되지 않아 코드는 모든 프로필에서 기본 꺼짐으로 두었다. 켜는 것은 `ticket-rush.warmup.enabled=true`다.
- 같은 부하 60초 예열이 통과한 것과의 차이는 쓰기 경로와 실제 트래픽 비율을 데웠는지로 추정하지만 시험하지 않았다.

#### 적용한 대응과 재측정 (2026-11-04, 최종 코드)

**1. 풀 고갈을 503으로.** 연결 풀에서 연결을 못 얻은 예외(`SQLTransientConnectionException`이 원인 사슬에 있음)를 503 `TEMPORARILY_UNAVAILABLE`과 `Retry-After` 5~10초로 응답하고, 요청마다 스택 트레이스 대신 한 줄(`DB 연결을 얻지 못해 503으로 응답합니다: ... (total=20, active=20, idle=0, waiting=200)`)만 남긴다. Redis 일시 장애(E26)와 같은 방식이다.
- 단위 테스트(분류기 4, 예외 처리기 2)와 e2e E31(풀 2개, 대기 250ms로 줄인 앱에서 테스트가 연결을 모두 쥐고 요청, 풀리면 회복)로 확인했다. 분기를 끄면 둘 다 실패하는 것도 확인했다.
- 실제 부하로도 확인했다: 풀 2개, 연결 대기 250ms로 줄인 앱에 흐름 120명/s를 60초. 풀 고갈 503 88건(한 줄 WARN, 스택 트레이스 없음), nginx의 5xx는 이 503 88건뿐이고 500은 0건이다. Hibernate가 자체로 남기는 WARN(`Connection is not available`) 90건은 그대로라 요청당 로그는 두 줄이다.
- 풀 3개, 연결 대기 3초(기본)에서는 같은 부하에서도 대기가 평균 8.5ms라 타임아웃이 나지 않았다. 타임아웃이 나야 이 경로를 탄다.

**2. 가득 찬 대기열의 거절 재사용.** 앱이 `QUEUE_FULL` 503에만 `Cache-Control: max-age=1`을 붙이고, nginx가 줄서기 경로에 한해 이 응답을 저장해 같은 공연의 줄서기에 다시 돌려준다. 등록 성공(201)과 IP 한도 거절(429)은 헤더가 없어 저장되지 않는다(자리가 있는 공연에 6번 등록해 서로 다른 토큰 6개, 모두 `MISS`, `ZCARD 6`). 단계 `R1`로 쟀다(대기열 상한 2,000명을 채운 뒤 거절만 되는 줄서기, 앱 1대 2코어, 부하기는 Docker 네트워크 안).

| 변형 | 앱 CPU 평균(1,000/s, 2,000/s, 4,000/s) | 2,000/s의 요청당 앱 CPU | 4,000/s의 nginx CPU | 4,000/s 처리량, QUEUE_FULL 비율, p95 |
|---|---|---|---|---|
| 기준선 | 43%, 56%, 115% | 0.273ms | 566% | 3,694/s, 85.5%(나머지는 nginx 동시 연결 상한 503), 436ms |
| 예외의 스택 트레이스 끔 | 43%, 51%, 105% | 0.247ms | 412% | 3,692/s, 90.3%, 374ms |
| nginx 재사용 1회차 | 5%, 5%, 14% | 0.009ms | 34% | 3,994/s, 100%, 0.8ms |
| nginx 재사용 2회차(최종 코드) | 11%, 9%, 4% | 0.032ms | 32% | 4,000/s, 100%, 0.6ms |

- 스택 트레이스를 끄는 것은 약 10%로 실행 간 흔들림 안이라 코드에 넣지 않았다. 거절 비용의 대부분은 예외가 아니라 요청 하나를 앱까지 보내 처리하는 기본 비용이다.
- 재사용 2회차는 k6가 보낸 209,954건 중 810건만 앱까지 닿았다. 만료 직후 몰린 요청이 잠깐 앱으로 가기 때문이다(캐시 잠금은 정상 등록을 한 줄로 세우므로 켜지 않았다).
- 거절은 실측 약 1.4초(6회 모두 1.37~1.46초) 유지된다. nginx가 만료를 초 단위 시계로 판정해 `max-age=1`이 실제로는 1~2초다. 그동안 대기열에 자리가 나도 거절이 이어지고, `Retry-After`는 그 시간 안의 요청이 모두 같은 값이다(클라이언트는 응답을 받은 때부터 세므로 재시도 시각 자체는 퍼진다).
- `k6/check-full-queue-cache.sh`가 MISS 다음 HIT, 응답 유지, HIT이 앱에 안 감, 만료 뒤 재요청, 다른 경로는 캐시 안 함을 점검한다(R1에서 자동 실행, 5개 모두 통과).
- ALB만 쓰는 구성에서는 nginx가 없어 이 효과가 없다.

- 각 조건 1~2회이고 같은 비교가 크게 흔들리는 환경이라 순서와 방향만 믿는다.

- **어느 값도 목표 99.9%에 닿지 못했다.** 가장 좋은 값이 1000의 2회차 99.45%다.
- 상한을 올리면 결과가 갈린다. 시작이 순조로우면 조금 나아지지만(500의 2회차 98.55%, 1000의 2회차 99.45%), 시작이 나쁘면 더 받아준 순번 조회가 앱 CPU와 힙을 채워 홀드와 결제까지 무너뜨리고(500의 1회차), 1000에서는 힙이 차서 앱이 죽었다. 상한은 오류를 줄이는 장치가 아니라 이런 연쇄를 막는 장치이고, 거절된 순번 조회는 `Retry-After`로 다시 시도할 수 있지만 죽은 앱은 그렇지 않다.
- 그래서 상한은 250으로 둔다. 순번 조회 가용성은 상한이 아니라 시작 직후 앱이 느려지지 않게 하는 쪽(예열, 점진적 트래픽 투입)이나 순번 조회 자체를 가볍게 하는 쪽에서 풀어야 한다. 또는 상한이 낸 503을 `Retry-After`로 재시도할 수 있는 거절로 보고 SLO에서 따로 세는 설계 판단이 있는데, 그러면 이번 위반이 SLO에서 사라지는 것이지 사용자 경험이 나아지는 것은 아니라서 바꾸지 않았다.

#### 순번 조회 가용성이 낮은 이유

최종 코드의 V2에서 순번 조회 가용성이 예열 없이 95.57%, 98.90%, 60초 예열 뒤에도 한 번 99.03%였다(목표 99.9%). 이유를 한곳에 정리한다.

**1. 실패의 정체는 nginx가 즉시 돌려보낸 503이다.** 앱의 500은 0건이었고 순번 조회 실패는 전부 nginx 동시 연결 상한이 낸 503(`SERVER_BUSY`)이었다(예열 없음 1회차 33,896건 / 764,315건 = 4.43%). SLO는 이 503을 실패로 센다. 사용자는 그 순간 순번을 받지 못했기 때문이다. 거절돼도 대기 순번은 유지되고 `Retry-After`만큼 뒤에 다시 조회하면 된다.

**2. 사람이 늘어서가 아니라 처리가 느려져서 걸린다.** 동시 요청 수는 도착 속도 x 처리 시간이다. 측정에서 도착 속도는 3,200/s로 처음부터 끝까지 일정했다. 상한 250이 걸리려면 평균 처리 시간이 250 / 3,200 = 약 78ms를 넘어야 한다. 평소 순번 조회는 p95 41ms(예열 없음 1회차 p99 152ms)라 평균이 한참 아래지만, 앱이 잠깐 느려지면 같은 도착 속도에서도 동시 요청이 쌓여 250을 넘고, 넘은 요청은 앱에 닿지 않고 바로 거절된다. 실제 오픈에서는 도착 속도도 함께 늘 수 있어 더 쉽게 걸린다. 이 상한은 앱 힙을 지키는 장치이고, 올리면 힙이 차서 앱이 죽었다(위 "순번 조회 동시 연결 상한을 올려 봤다").

**3. 앱이 느려지는 구간이 두 가지 보인다.** nginx 로그 기준으로 느린 요청(100ms 이상)이 가장 많이 몰린 5초 구간이다(부하 시작 기준).

| 실행 | 순번 조회 가용성 | 상한이 낸 503 | 느린 요청이 가장 많이 몰린 구간 |
|---|---|---|---|
| 예열 없음 1 | 95.57% | 33,896 | +6초 1,955건, +11초 3,723건. 끝 무렵 +206~216초에도 5초마다 2,000건대 |
| 예열 없음 2 | 98.90% | 8,463 | +9초 2,212건 |
| 60초 예열 1 | 99.95% | 398 | 최대 +204초 280건 |
| 60초 예열 2 | 99.03% | 7,389 | +157~187초에 5초마다 600~1,000건대 |

- **시작 직후(약 10초)**: 예열 없는 실행에서 보인다. JIT가 덜 데워진 앱에 전체 부하가 한꺼번에 들어와 앱 CPU가 한도(2코어)에 닿고 연결 풀 대기 스레드가 최대 323개까지 쌓였다(60초 예열 1회차는 0). 이쪽은 예열이나 점진적 트래픽 투입으로 줄일 여지가 있다.
- **부하 후반(약 150~215초)**: 예열 없는 1회차와 60초 예열한 두 실행에서 보인다. **원인은 확인하지 못했다.** 예열로는 줄지 않았다(60초 예열 2회차가 99.03%). 후보는 좌석이 차며 홀드 충돌 재시도가 늘어나는 시기와 겹친다는 점(앞선 측정에서 정상 상태의 Hikari 풀이 120~200초에 가득 찼던 것과 같은 시기), 그리고 힙이 한도(512MiB)에 가까운 482MiB까지 찬 점이다. 어느 쪽도 가려내지 못했다.
- 따라서 "시작 직후만 안정시키면 해결된다"고는 말할 수 없다. 앞쪽 갈래만 예열로 줄고 뒤쪽은 따로 원인을 찾아야 한다.

| 응답 `code` | 낸 곳 | 언제 | SLO에서 |
|---|---|---|---|
| `SERVER_BUSY` | nginx | 순번 조회 동시 250개, 줄서기 동시 500개를 넘음. 앱에 닿지 않음. `Retry-After` 3, 5, 7, 10초 | 실패로 센다 |
| `QUEUE_FULL` | 앱 | 대기열이 50만 명 상한에 닿음. 거절을 nginx가 1~2초 재사용 | 의도된 거절(제외) |
| `TEMPORARILY_UNAVAILABLE` | 앱 | Redis 일시 장애, DB 연결 풀 고갈. `Retry-After` 5~10초 | 실패로 센다 |
| `PAYMENT_GATEWAY_UNAVAILABLE` | 앱 | 결제사 5xx, 타임아웃, 서킷 OPEN. 결제는 `PENDING` 유지 | 실패로 센다 |

**5. 관측의 한계.** nginx 접근 로그는 100ms 이상이거나 500, 502, 504인 요청만 남기고, 상한이 내는 503은 즉시 돌아가므로 거기 남지 않는다. 그래서 이 503이 초 단위로 어떻게 분포하는지는 직접 보지 못했다. 위 표는 느린 요청의 분포와 예열한 실행과의 비교로 추정한 것이다. 확인하려면 k6의 요청 기록(`--out csv`)을 받아 초 단위로 세어야 한다(하지 않음). 측정 원본(`k6/results`)은 git에 올리지 않는다.

**6. 하지 않은 것.** 상한이 낸 503을 SLO에서 재시도 가능한 거절로 따로 세는 설계(위반은 사라지지만 사용자 경험은 그대로라서 하지 않음), 부하 후반 구간의 원인 규명(GC 로그, Hikari 대기 시계열, 홀드 충돌률을 같은 시각으로 맞춰 보기), 상한 503의 초 단위 분포 확인.

### 측정 경로 오류 (바로잡은 것)

초기 측정에서는 "앱 한 대는 새 사용자 40명/s까지만 지키고, 60명/s에서 좌석 배치 p95 3.9초, 80명/s에서 붕괴(줄서기 가용성 82%)"로 나왔다. 그 측정은 **호스트의 k6가 Docker Desktop의 포트 포워딩을 거쳐** 요청한 것이었고, 이 경로가 큰 응답(250KB)을 초당 수십 건 넘게 받을 때 먼저 한계가 되었다.
- 근거: 좌석 배치만 초당 60건 걸었을 때 호스트 경로는 p95 1,570ms(TTFB 55ms + 받는 시간 1,479ms)인데, 이때 앱 CPU는 1.6%, nginx CPU는 15%로 앱은 쉬고 있었다. 같은 요청을 Docker 네트워크 안에서 보내면 p95 4ms다.
- 그래서 앞선 "60명/s에서 배치 3.9초"는 서버 용량이 아니라 측정 경로의 한계였다. "80명/s 붕괴"는 같은 조건(캐시 없음)에서 Docker 네트워크 안의 부하기로 다시 걸었을 때 재현되지 않았다. 호스트 경로의 느린 수신이 연결을 오래 붙들어 서버 쪽에 영향을 준 것과 일치하지만, 그것이 원인이라는 것은 확인하지 못했다.
- 이 단계 이후의 측정은 모두 부하기를 Docker 네트워크 안에서 돌린다(`K6_DOCKER=1`이 V1의 기본).

### 해석

- **앱 한 대(2코어)는 새 사용자 120명/s + 읽기 300/s에서도 모든 SLO를 지켰다.** 한계는 찾지 못했다. 이 위로는 승격 상한(초당 100)이 먼저 병목이라 새 사용자를 더 걸어도 홀드와 결제 부하는 초당 100에서 멈추고 대기 시간만 늘어난다. 그래서 더 높은 속도를 걸어 한계를 찾는 것보다 승격 상한을 올릴지의 설계 판단이 먼저다.
- **README 목표 규모(대기자 50만 명, 순번 조회 3,200/s, 줄서기 2,000/s, 승격 100/s의 홀드와 결제, 읽기 300/s)를 앱 1대(2코어)가 같은 부하 60초 예열 뒤에 모든 SLO로 버틴 것은 3번 중 2번이다.** 나머지 한 번과 예열 없는 실행은 순번 조회 가용성이 99.9%에 못 미쳤고, 실패는 nginx의 순번 조회 동시 연결 상한이 낸 503이다. 최종 코드에서 앱 CPU 평균은 116~144%(한도 200%)이고, 덜 데운 앱에 같은 부하를 한꺼번에 걸면 처음 40초에 깨지는 것은 그대로다. 병목은 시작 직후의 앱 CPU와 DB 연결 풀(20)로 관측됐고 DB 자체는 아니었다. 정상 상태 용량의 상한은 재지 않았고, 정상 상태에서도 Hikari 풀이 가득 차는 순간이 있었다.
- 줄서기 2,000/s와 순번 조회 3,000/s(대기자 10만)는 p95 1ms로 충족했다. 출고 nginx의 동시 연결 상한(500, 250)은 응답이 1ms라 걸리지 않았다(제외 0건).
- 힙 최대가 266~275MiB(앱 1대)로 상한(512MiB)에 여유가 있어 힙을 늘릴 근거가 없다. GC 정지는 앞선 호스트 경로 실행에서 60초당 0.27~1.84초, 평균 정지 2~6ms였고 이번 실행에서는 따로 재지 않았다.

### 하지 않은 측정

- 예열이 전혀 없는 첫 요청부터의 부하는 재지 않았다. V2의 "기본" 실행은 가벼운 예열만 거친 상태이고, "충분히 데운" 실행은 같은 부하 60초를 먼저 걸었다. 초기 측정의 "재시작 직후 80명/s에서 대부분의 API가 p95 1초 초과"는 호스트 경로의 측정이라 신뢰하지 않는다.
- 같은 부하 60초 예열은 3번 반복했고 2번 통과했다. 점진적 트래픽 투입이나 쓰기 경로까지 데우는 예열의 효과는 재지 않았다. 순번 조회 동시 연결 상한은 예열 없는 실행에서만 올려 봤고(2회씩) 60초 예열한 실행에서는 올려 보지 않았다.
- 용량의 위쪽 한계(앱 CPU나 Postgres가 실제로 포화하는 도착률)는 찾지 못했다. 앱 2대가 느린 현상은 시험 환경의 CPU 부하 영향이 유력하지만 느려지는 메커니즘은 확인하지 못했고, 앱이 별도 호스트에서 도는 구성은 재지 못했다(위 "앱 2대" 참고).
- 실제 Toss의 지연 분포는 반영하지 못했다(가짜 PG 0ms).

## 한계

- 목표 규모(대기자 50만 명)를 서버 증설 없이 받을 수 있는지, 증설이 필요한 이유와 모르는 것은 `docs/capacity.md`에 정리했다.

- 값은 가짜 PG와 한 대의 Mac에서 확인한 초안이다. 처음 4주의 운영 지표로 조정한다.
- 측정 환경은 한 대의 Mac이다. 부하기와 서버가 같은 호스트(부하기는 Docker 네트워크 안)에서 돌아 호스트 상태에 따라 결과가 흔들린다. 대부분 조건당 1회라 반복 분산은 모른다(앱 1대 대 2대 비교만 2회 반복했고 두 번 모두 같은 방향이었다).
- 결제 지연은 가짜 PG 기준이다. 실제 Toss의 지연 분포는 반영하지 못했다.
- V2의 승격은 줄 앞 토큰을 미리 활성으로 만들어 흉내 낸 것이다. 승격 스케줄러가 50만 명 대기열에서 도는 비용은 V2에 들어 있지 않다.
- V2의 줄서기 폭주 2,000/s는 대기열이 가득 찬 뒤에도 계속 들어오는 최악의 가정이다. 실제 클라이언트가 `Retry-After`를 지키면 이보다 적다.
