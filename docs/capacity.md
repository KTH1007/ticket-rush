# 목표 규모와 서버 증설

"대기자 50만 명"을 서버를 늘려야만 받을 수 있는지, 무엇을 측정했고 무엇을 모르는지 정리한다. 측정 방법과 결과의 상세는 `docs/slo.md`에 있다.

## 한 줄 요약

- 증설이 용량 때문에 반드시 필요하다고 측정으로 보인 것은 없다. 앱 1대(2코어)가 데운 상태에서는 목표 규모를 대체로 버텼다.
- 그래도 운영에서는 앱 2대 이상을 권한다. 여유가 적고, 한 대는 배포나 장애 때 서비스가 멈추는 단일 장애점이기 때문이다.
- 앱을 늘리면 용량이 느는지는 이 환경에서 확인하지 못했다.

## "50만 명"은 무엇인가

| 항목 | 값 | 뜻 | 어디서 제한하나 |
|---|---|---|---|
| 최대 대기열 유입 | 500,000명 | 대기열에 서 있는 사람의 수. 동시에 처리하는 사람이 아니다 | `ticket-rush.queue.max-waiting`. 닿으면 새 줄서기를 `QUEUE_FULL` 503으로 거절 |
| 대기열 등록 | 2,000 TPS | 줄서기를 받는 속도. 50만 명이 차는 데 약 250초 | 넘치면 nginx 동시 연결 상한(500)이나 대기열 상한이 503으로 돌려보냄 |
| 승격 | 100 TPS | 대기열에서 나와 DB를 쓰는(홀드, 결제) 속도 | `ticket-rush.queue.promotion-budget-per-second`. Redis에서 세므로 앱이 여러 대여도 합계가 이 값을 넘지 않는 설계 |
| 좌석 | 30,000석 | 1인 최대 2매라서 승격된 1만 5천 ~ 3만 명이 가져가면 매진 | |

- DB를 쓰는 사람은 승격된 사람뿐이라 DB 부하는 대기자 수가 아니라 승격 속도(100/s)로 정해진다.
- 대기자 50만 명 중 대부분은 매진 전에 승격되지 못한다. 대기열은 많은 사람을 한꺼번에 처리하는 구조가 아니라 속도를 조절하는 구조다.
- 대기자가 쓰는 자원은 Redis 메모리(50만 명에서 약 100~112MiB)와 순번 조회 요청이다.

## 앱 1대(2코어)로 측정한 것

README 목표 규모 전체(V2: 대기자 50만 명 상태에서 순번 조회 3,200/s, 줄서기 2,000/s, 승격 100/s의 홀드와 결제, 읽기 300/s)를 한 대에 걸었다. 승격은 줄 앞 토큰을 미리 활성으로 만들어 모사했다.

| 자원 | 측정(최종 코드의 V2 4회) | 해석 |
|---|---|---|
| 앱 CPU | 평균 116~144%(한도 200%) | 여유가 적다 |
| 앱 힙 | 최대 389~482MiB(한도 512MiB) | 여유가 적다. 순번 조회 상한을 1000으로 올리자 힙이 차서 앱이 죽었다 |
| Postgres CPU | 평균 21~32% | 병목이 아니다 |
| Redis CPU | 평균 13~15% | 병목이 아니다 |
| 결과 | 모든 SLO 충족 4번 중 1번. 나머지는 순번 조회 가용성 95.57~99.03% | 원인은 `docs/slo.md`의 "순번 조회 가용성이 낮은 이유" |

- 순번 조회는 대기자 수에 비례해 늘어난다. 서버가 순번에 따라 조회 간격을 알려주는 정책이 이미 있다(순번 100위 안은 2초, 그 밖은 앞까지 걸리는 시간의 1/4을 15초 ~ 5분 사이로, 지터 ±20%). 대기자 50만 명이 이 간격으로 조회하는 양이 계산상 약 3,158/s이고, V2는 이보다 약간 높은 3,200/s를 걸었다.
- 한계: 한 대의 Mac, 가짜 PG, 조건당 1~2회.

## 증설이 필요한 이유 (용량만이 아니다)

1. **단일 장애점이다.** 앱이 한 대면 배포, 재시작, 장애 때 서비스가 멈춘다. 용량과 무관하게 2대 이상이 필요하다.
2. **여유가 적다.** CPU와 힙 모두 한도에 가깝다. 대기자가 늘거나 조회가 잦아지면 순번 조회가 먼저 한계에 닿는다.
3. **새 인스턴스는 시작 직후 흔들린다.** 예열 없이 시작하면 처음 10여 초에 앱이 느려지고 nginx 동시 연결 상한이 순번 조회를 거절한다. 인스턴스가 여럿이면 새로 띄운 것에 트래픽을 점진적으로 얹을 수 있다(ALB slow start 등). 이 방식은 검증하지 못했다.

## 증설 없이 줄일 수 있는 것

| 방법 | 상태 |
|---|---|
| 순번 조회 간격을 순번에 비례해 늘림 | 이미 적용. 더 줄이려면 `poll-interval.far` 하한을 키울 수 있지만 순번 갱신이 느려진다 |
| 가득 찬 대기열의 줄서기 거절을 nginx가 재사용 | 적용. 거절 요청당 앱 CPU 0.273ms -> 0.009~0.032ms |
| 좌석 배치 nginx 캐시 | 적용. 앱 CPU 93~147% -> 49~53% |
| 앱 코어를 2에서 4로(서버 대수가 아니라 크기) | 하지 않음 |
| 클라이언트가 `Retry-After`를 지킴 | 클라이언트 쪽 일. 서버는 값을 흩뜨려 준다 |

## 모르는 것

- **앱 2대가 용량을 늘리는지.** 이 환경(한 대의 Mac)에서는 2대가 1대보다 느린 경우가 많았다(11번 중 10번). 앱을 늘리지 않고 앱이 아닌 CPU 부하만 얹어도 같은 느려짐이 재현돼 환경의 CPU 경합이 유력하지만, 메커니즘은 직접 보지 못했고 앱이 별도 호스트인 구성은 재지 못했다. "2대면 2배"라고 말할 근거가 없다.
- nginx 동시 연결 상한은 nginx 하나가 세는 합계라 앱이 2대가 되면 값을 다시 정해야 한다. 설정 파일 주석은 대략 두 배로 보지만 이번 측정에서는 확인하지 못했다.
- 실제 50만 명의 재시도 패턴, ALB, 실제 Toss의 지연.
- 부하 후반(약 150~215초)에 앱이 느려지는 원인. 증설로 풀리는 문제인지 모른다.

## 면접에서 말한다면

"50만 명은 대기자 수라서 앱 1대와 Redis 약 100MiB로 쥘 수 있었고, 승격 100/s로 DB 부하를 조절했습니다. 다만 앱 1대는 CPU와 힙 여유가 적고 단일 장애점이라 운영에서는 2대 이상이 필요합니다. 증설이 용량을 늘리는지는 이 환경에서 측정하지 못했습니다."
